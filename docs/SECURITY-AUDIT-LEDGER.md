## 🛡️ 安全边界：被第三方按我们自己的契约审了两轮，外加一次社区提报（v20.2.4 / v20.2.5）

一位第三方独立安全复审给这棵树打了 **C（有条件不通过）**，27 项发现。我方**逐条核验，零误报，全部认账并已整改**。

它审的不是「有没有 SaaS 级隔离」——README 一直写着这不是互不信任客户的隔离层，报告也明确保留了这条边界。它审的是**我们自己写下的契约**能不能兑现。结果是三句宣称被当场推翻：

| 我们写过 | 实况 |
|---|---|
| `local` 档「零 token、零外部网络」 | 九个模块直接调 LLM，一个都不看档位 |
| 「每条在线读写路径都有二维作用域」 | 一批次级端点是裸的 `WHERE id=?` |
| 「三层注入防御」 | 包装函数看到正文里有 `<memory>` 就**整个不包装** |

**第三条最值得说**：那是一道**能被它所保护的内容自己关掉的防御**。攻击者只要在记忆里写一个 `<memory>`，整个注入框架静默跳过。现在改成**编码**而不是检测——闭合标记带一次性随机口令（结构上伪造不了），正文里的边界记号一律中和（插零宽字符，不删内容）。

**做法不是「改 27 个地方」，是把 27 个症状收敛到 5 条原则上**，每条配一个结构守卫，让下一个同类缺陷在进仓前变红：

| # | 原则 | 被抓的反面 |
|---|---|---|
| 1 | 单一真相源，不靠调用点自觉 | 档位谓词接在主链上，九个调用点各自裸奔 |
| 2 | 补能力，不改措辞 | 门禁写在 `main()` 里，然后文档说「别用 `uvicorn app`」 |
| 3 | fail-closed 是默认 | `except Exception: return True`；开关拼错静默降级 |
| 4 | 边界靠编码，不靠检测 | 用「字符串里有没有标记」判断是否已包装 |
| 5 | 守卫能抓住下一个同类 | 测试替身比生产函数少两个参数，缺陷因此隐形 |

**几个实测数字**（不是设计稿）：

- 无凭据启动公网监听：**真起 `uvicorn` 子进程四场景全对**，含「`--host 0.0.0.0` 在开始接收请求前失败」——那是 uvicorn 自己的命令行参数，环境变量看不到，所以判据里也扫了 argv；
- 登录失败表：10,000 个不同 IP 从 **0.433 秒 / 无上限** 变成 **0.011 秒 / 4096 条硬上限**，表满转本窗口全局节流、下一分钟自动解除；
- 通用状态词误伤：「请关闭通知（与邮箱和灯光都无关）」此前让两条互不相关的事实**同时失效**，现在是 **0**；
- 类型分档在具名记忆库下完全失效（时效分 0.0111 而非 1.0000，被当普通事实打折九十倍）——**这是本版自己的缺陷**，且它躲过了本版自己的 50 条用例，因为测试替身比生产签名宽松。

### 第二轮（v20.2.5）：审出来的第一条，是我们上一轮的**假修复**

同一位第三方又审了一遍整改结果，评级仍是**有条件不通过**。最重的一条不是新缺陷，是**我们自己的账**：

> 上一轮那条「refine 候选跨记忆库收窄」—— 代码**算出了** SQL 的作用域子句和参数，**一个字都没有拼进 SQL**。而它上一行的注释写着「已按记忆库轴收窄」，结案陈词把它列为已修，**且没有任何测试盯着它**。

注释、结案陈词、自我复核三层都放行了，只有一个共同原因：**没有测试**。所以这一轮的判据全部换成**集合相等**（`{A,C}` 而不是「返回了 A」——后者对「B、D 也混进来」毫无区分力，而那正是这条缺陷的形态）。

另外两条 P0 都是**「没有症状」的那一类**：

| 缺陷 | 为什么难发现 |
|---|---|
| 删除只有「成功」一种结果 | 任何一层失败都记 `committed` 并回 `{"status":"ok"}`；HTTP 出口硬编码这个字面量，连上一轮加的 `not_cleared` 都从没到达调用方 —— **那条修复因此也是半假的** |
| 交付模板不设运行目录 | 装成 wheel 后数据落进 `site-packages` 里的包目录，而挂载的是 `/app/data`。服务正常起、接口正常答、数据写进容器层，**重建即丢**，全程零报错 |

现在：删除结果三态 **`committed`→200 / `partial`→**207** / `failed`→500**，`failed_layers`（本次真失败）与 `not_cleared`（矩阵预声明豁免）分开报，WAL 只在全绿时提交、否则留待重放；Dockerfile 与 systemd 显式交接四个运行目录变量，`/health` 新增 `runtime_paths` 报**实际打开的路径与可写性**。

**还有一条是我们自己的守卫在骗自己**：这一轮把 Ruff 加进推送门禁（此前根本没装，装上当场抓到一个 `F821` —— 一段读配置的逻辑因为用了未定义的名字、异常被吞，**从来没成功执行过**）。但门禁的第一版在**没装 ruff 的环境里返回「零命中」**，于是它报「扫过了，通过」。「扫过了」和「扫不动」长得一模一样 —— **一个在依赖缺失时静默变绿的守卫，比没有守卫更危险：它还替你签了字。** 现在缺工具就诚实跳过，并且判据与探测器共用同一份实现。

### 第三轮：一位社区网友的 Agent 提了一个我们自己没发现的 Bug

[Issue #5](https://github.com/monkey2jack/aiduMEI/issues/5)（提报：小赫 Hermes Agent 代拾予 · 小克审计 Agent）指出：
混合召回链路**没有任何最低分门槛**，零命中/弱命中条目可以靠时效、可靠性、访问热度凑分填满结果集，稀释真正相关的召回。

**属实。** 我们复核时把数字重新跑了一遍（跑生产打分函数现算，不是推导）：

| 情形 | 复合总分 |
|---|---|
| 零证据条目（向量分与 BM25 分双零）· 默认 | 0.2015 |
| 零证据 · 事实类查询 ×1.35 | 0.2720 |
| 零证据 · 高信任 + 高访问热度 | 0.4000 |
| 零证据 · 高信任高热度 + 事实类查询 | **0.5400** |
| ↑ 再叠 ignition 增益 ×1.5 | **0.8100** |
| 参照：**真相关**条目（vec .8 / bm25 .5） | 0.6065 |

**最后两行是这次修复的分水岭**：零证据条目的**上限已经越过真相关条目**。
这说明 issue 建议的「设一道最低总分门槛」**单独用不够** —— 能拦住 0.81 的阈值必然连真结果一起杀。

所以修法分两层，都落在打分函数这**一个出口**（`engine` 与 `recall_funnel` 两条链同时受益）：

- **证据闸门（默认开）**：向量分与 BM25 分**双零**的候选直接出局，不进重排（顺带省 token）。
  零证据条目与查询之间不存在任何可解释的关联，放它进结果集没有「可能是对的」这种情形 —— 因此这一道不存在误杀风险。
  ignition 命中的条目**不会被误杀**：它的分数走的就是向量分那个入口。
- **复合总分门槛（默认 0.0，即关闭）**：机制建好、可配置、有遥测，但**默认不生效**。
  为什么不照 issue 建议直接设 0.3：实测三 token 查询命中其中一个（bm25 = 1/3）总分约 **0.285**，
  落在 0.3 下方 —— 那是**合法的弱召回**，不是垃圾。这个阈值要用生产侧真实查询分布算分位数才能定，
  所以本次先把观测做出来（响应里带分数直方图），值等数据够了再开。
  **拍脑袋的常数会把真记忆判成「没有」** —— 这是本仓 v20.1 就写下的裁决，不是这次才想到的。

> **三道分数闸门，轴与层位各不相同，别当重复实现**：
> `AIDUMEM_RECALL_SCORE_FLOOR`（**向量分**轴 · `/search` 响应层）、
> `AIDUMEI_RECALL_MIN_HYBRID`（**复合总分**轴 · 打分层，覆盖所有调用方含 MCP）、
> 以及传播链与自进化各自的门槛（不在召回链上）。源码里两处互相留了交叉引用，并有守卫盯着。

**实机实测又改了一次方向 —— 这一条最值得看**：上面那道证据闸门，在**活库上几乎不触发**。
向量检索对任何候选都会给出一个大于零的相似度，`vec = 0` 这种情形只在向量腿降级时出现。
生产库实测：

```
查询「复盘召回质量」        → 真相关 0.7165 · 无关 0.4062 · 无关 0.3870
查询「量子色动力学的渐近自由」 → 三条全无关 0.2862 / 0.2819 / 0.2362
```

真正的矛盾在别处：部署方**早就**用 `AIDUMEI_RECALL_VERDICT_THRESHOLD` 声明了「低于这个分不可信」
（生产实际配的是 **0.46**，拿真实查询分布标定出来的），系统也照此把整批结果判成 `not_found`，
**却仍然把它们原样返回** —— 「我知道这批不靠谱」和「我照样给你」同时成立。那才是 issue 描述的病。

所以最后这一刀是：**召回下限未显式配置时，回落到那个已标定的阈值**。
不是新造一个默认值 —— 一个部署对「多少分算可信」只该有一个说法。
以 0.46 为下限重放上面两个查询：前者只留真相关那条，后者空手返回，两个同时正确。
要回到旧行为，显式写 `AIDUMEM_RECALL_SCORE_FLOOR=0`。

**没有顺带做的事**：BM25 的 CJK 匹配用的是子串（查「量」会命中「用量」）。
这是真问题，但改它属于**检索行为变更**，需要跑分对照，不夹带进一个 bug fix。已单独立项。

## 🧬 第四轮（v20.5.0 正式版）：Preview 外审 —— 两条核心承诺被实测推翻，连「已验证」的牌子一起

v20.5 Preview 发布后，一轮用户视角审计（真实 HTTP 端点复现 + 生产库只读对账）加两轮外部代码审计，把本版两大卖点各推翻了半边。这一轮的教训不是「有洞」，是**有个洞还挂着「已验证」的牌子**。

### 🔴-1 谱系串链：upsert 之后信了 `lastrowid`

`INSERT ... ON CONFLICT DO UPDATE` 冲突命中时，SQLite 的 `lastrowid` **不是被更新行的 id**（残留上一条 INSERT 的 id 或 0）。federation writer 与 legacy `/facts/add` 两条写入路径都拿它当谱系 `memory_id`，于是：A 事实的版本记到 B 的链上；同一 key 反复写在 `fact:<id>` 与 `fact:<key>` 两条链上永远分叉；**生产库实证两条幽灵链**（`fact:4351/4352`，指向不存在的事实行）。

而 `verify_lineage_integrity` 对这一切**全绿**——它只校验链内哈希咬合与版本连号，从不校验链指向的事实行是否存在、链尾哈希是否等于行的实际内容。**验证端点的绿灯制造了虚假信心**，这比缺陷本身更危险：它会让后续的审计结论建立在假证词上。

修法：两条写入路径改 `RETURNING id`（SQLite<3.35 回退唯一键回查），绝不信任 lastrowid；verify 端点补**存在性对账 + 链尾内容对账**（含 DELETE/FORGET 终链语义）；存量行由 v5 迁移回填内容哈希并补 `BACKFILL` 基线（如实声明历史不可追，不再是「假创世块」）。守卫：同 key 三写单链 1→2→3、交错写不串链、幽灵链/内容不符/非法形态必报 broken。

### 🔴-2 自签授权 + 身份自报：「跨 Agent 默认拒绝」一条 POST 就能拆掉

两个独立缺陷叠加使整个零信任模型失效：① `POST /federation/grants` 无任何调用者校验——任何能打 API 的人都能以任意受害者名义给自己（含通配 `*`）签发 `read,write,delete` 全套权限；② `_enforce_grant` 把「`caller_agent_id` 为空」判为单机回环放行，而被访问方 `agent_id` 是查询参数——**不传 caller + 传 victim 的 agent_id = 冒充本人**，实测明文读到他人私密记忆。

v20.4.1 时这不成立（那时跨 Agent 判据是 `shared` 单方声明，没有零信任承诺）；v20.5 把「跨 Agent 默认拒绝（403）」写进了产品定位，缺陷的严重度随之升级为**卖点本身不成立**。

修法：grants 三端点接入调用者校验（caller 必填；caller==grantor 或 admin 才能签发/撤销；`created_by`/`revoked_by` 从 caller 派生，不再吃请求参数）；`_enforce_grant` 空 caller 默认 403，存量单机走显式逃生门 `AIDUMEI_ALLOW_IMPLICIT_CALLER=1`；谱系/授权查询端点同步补租户归属校验（🟡-6）。守卫：冒充形态 403、自签形态 403、合法形态 200、逃生门语义、撤销身份派生。

**残留边界如实写明**：caller 身份仍是自报参数，未与 Bearer Token/mTLS 做密码学绑定——本版的授权闭环防的是**同一可信宿主边界内 Agent 的越权与误操作**，并把审计身份钉成可溯源；token→身份绑定是 v21 路线图项（外审 Luna 的演进建议，与本修复同向）。

### 同批收口（用户审计 🟡 系列）

- **🟡-1** crud `/update` 谱系腿对 mem0 UUID 静默空转（命中网只有 `id OR fact_key`）：放宽到与删除路径同构的键形态，「形似 facts 引用却 0 命中」记 WARNING，纯向量记忆如实报 `not_a_fact`；端到端用例真正驱动 `POST /update`（旧用例只复刻 SQL 形状——**「守卫射程 ≠ 缺陷分布」第六次**，同一个病）。
- **🟡-3** `expires_at` 非法值曾被静默视为永久：创建即拒绝，存量非法值按已过期处理并 WARNING。安全特性的降级方向必须朝更严。
- **🟡-4** `_match_scope` 只修了 4 个已知维度的 fail-closed，未知维度名（拼错的/未来的）仍静默通配：未知维度一律拒绝，创建时即校验 scope 语法。
- **🟡-5** 谱系治理：`UNIQUE(memory_id, version)` 兜底（沉默分叉变显式报错）；删除路径补 DELETE 终链（「删过什么」此前完全不留痕）；`diff_summary` 去除 fact_key 明文（删除权行使后谱系不再留用户原话）。
- **措辞归真**：「不可篡改的版本链」改为「**可检测篡改**（tamper-evident）的密码学谱系」——拿到 SQLite 写权限者理论上可重算整条链；强不可抵赖（签名/外部锚定/WORM）属 v21 路线图，不在本版承诺。
